# ข้อกำหนดการใช้บริการ tiwhub — ต้นฉบับและแผน versioning

> **สถานะ: รอตรวจทานทางกฎหมายและอนุมัติก่อนเผยแพร่** เนื้อหาตัวอย่าง v1.0 ที่ระบบแสดงยังไม่ใช่คำแนะนำทางกฎหมาย ผู้ดูแลต้องยืนยันผู้ให้บริการ/คู่สัญญา ขอบเขตความรับผิดชอบ เงื่อนไขคอร์ส การคืนเงิน ช่องทางติดต่อ และกฎหมายที่ใช้บังคับก่อนเปิดใช้จริง ห้ามถือการยอมรับข้อกำหนดเป็นความยินยอม PDPA

## วัตถุประสงค์และขอบเขต

ให้ใช้เอกสารฉบับนี้เป็นแม่แบบสำหรับข้อกำหนดของบริการ tiwhub ใน **CMS (หน้าเผยแพร่สาธารณะ)**, **Front (ผู้ดูแล/พนักงาน/ผู้ใช้ระบบเว็บ)** และ **LineLiff (ผู้ปกครอง)** โดยมีเอกสารและ version เดียวกันทุกช่องทาง ข้อความภาษาไทยและอังกฤษต้องมีความหมายเทียบเท่ากัน การเปลี่ยนภาษาไม่เปลี่ยน version หรือผลการยอมรับ

แยกเอกสารต่อไปนี้อย่างชัดเจน:

- **Terms of Service / ข้อกำหนดการใช้บริการ** — ข้อตกลงการใช้แพลตฟอร์มและบริการ
- **Privacy Notice / ประกาศความเป็นส่วนตัว** และ **PDPA consent / ความยินยอม** — แจ้งการประมวลผลและบันทึกความยินยอมตามวัตถุประสงค์ที่เกี่ยวข้อง การยอมรับ Terms ไม่ใช้แทน consent

## เนื้อหาฉบับ v1.0 ที่ปรับสำหรับแพลตฟอร์ม

เนื้อหาที่ API เสิร์ฟอยู่ใน [API/Legal/terms-v1.0.json](../API/Legal/terms-v1.0.json) และหน้าเผยแพร่ใน [CMS/lib/terms-v1.0.json](../CMS/lib/terms-v1.0.json) ต้องตรวจให้ตรงกันก่อน deploy ทั้งสองไฟล์มี:

1. บัญชี ข้อมูลที่ถูกต้อง และความรับผิดชอบต่อข้อมูลเข้าสู่ระบบ
2. ผู้ปกครอง/ผู้แทนโดยชอบธรรมดำเนินการแทนผู้เยาว์ โดยไม่สันนิษฐานว่าความยินยอมตามกฎหมายเกิดขึ้นแล้ว
3. การใช้งานตามสิทธิ์และข้อกำหนดการซื้อ/ชำระเงินที่สถาบันแจ้งก่อนทำรายการ รวมทั้งกฎหมายที่ใช้บังคับ
4. การแยกเจ้าของสิทธิซอฟต์แวร์แพลตฟอร์ม ออกจากเจ้าของเนื้อหาที่สถาบันหรือผู้สอนนำเข้า
5. ความพร้อมใช้งานและผลการเรียน โดยไม่รับประกันผลเฉพาะ
6. การอ้างอิงประกาศความเป็นส่วนตัวแยกจาก Terms
7. การระงับ/ยุติการใช้งานโดยคำนึงถึงกฎหมายและการแจ้งเหตุเมื่อทำได้
8. การประกาศ version ใหม่และการขอให้ผู้ใช้ยอมรับโดยชัดแจ้งก่อนใช้งานต่อ — **ห้ามใช้ continued use as implied acceptance**

## การแสดงผลในแต่ละแอป

| Surface | วิธีแสดง / การยอมรับ |
| --- | --- |
| CMS | หน้าสาธารณะ `/terms?lang=th` และ `/terms?lang=en` แสดง version, วันที่มีผล, ภาษา และเนื้อหาครบทุกหัวข้อ; footer เชื่อมถึงหน้า |
| Front | ตอนสมัครแสดง Terms จาก API และ checkbox ยอมรับแยกจาก PDPA; หลัง login ตรวจ current version และบังคับหน้า re-accept ก่อนหน้า protected; API ปฏิเสธ registration หากไม่ส่ง accepted/version ปัจจุบัน |
| LineLiff | หลังตรวจ LINE identity แสดง Terms ก่อน bind/ใช้ข้อมูลผู้เรียน; ยอมรับพร้อม version ก่อนดำเนินการ link code; API ตรวจสถานะก่อนให้บริการ endpoint ผู้ปกครอง |

แอปทั้งหมดต้องมีตัวเลือกไทย/English, loading/error/retry state และไม่ยอมรับอัตโนมัติเมื่อ fetch เอกสารไม่สำเร็จ ผู้ใช้ที่ไม่ยอมรับต้องออกจากระบบหรือหยุดขั้นตอนนั้นได้

## Versioning และการออกฉบับใหม่

- รูปแบบเลข version: `MAJOR.MINOR` เช่น `1.0`, `1.1`, `2.0`; ทุกการแก้เนื้อหาที่ต้องขอความยอมรับใหม่ต้องออก version ใหม่ ห้ามแก้ทับไฟล์เดิม
- เก็บไฟล์ immutable `API/Legal/terms-vX.Y.json` และสำเนาสำหรับเผยแพร่ `CMS/lib/terms-vX.Y.json`; ปรับ `Legal:Terms:CurrentVersion` และ map `Legal:Terms:Documents` ใน API config พร้อมชี้ `CMS/lib/terms-current.ts` ไปยังไฟล์ CMS version ที่อนุมัติแล้ว
- ตรวจว่าข้อความ TH/EN หัวข้อ วันที่มีผล และ version ตรงกันทั้งสองแอป ใช้ JSON schema เดียวกัน และคำนวณ SHA-256 จากไฟล์ canonical ของ API
- ก่อน deploy ให้ legal/product อนุมัติข้อความ วันที่เริ่มมีผล กลุ่มผู้ใช้ที่ต้องยอมรับ และแผนแจ้งผู้ใช้ เก็บฉบับเดิมไว้อ่านย้อนหลัง
- หลังเปลี่ยน current version ระบบถือว่า acceptance version เก่าไม่เพียงพอ บังคับ re-accept และเก็บเหตุการณ์ acceptance ใหม่ ไม่ยอมรับโดยปริยาย
- เปลี่ยน version กลับหรือ rollback ต้องเป็นการตัดสินใจที่บันทึกไว้ และต้องไม่ลบ/เขียนทับประวัติ acceptance

## Acceptance audit log

ตาราง `terms_acceptances` บันทึกหนึ่งรายการต่อ user + document type + version โดยอย่างน้อยเก็บ:

- `user_id`, `parent_id` (เมื่อเป็นผู้ปกครอง), `actor_type`, `actor_id`
- `document_type`, `document_version`, ภาษา (`th`/`en`), `content_sha256`
- `accepted_at` UTC, IP เมื่อมี, user-agent เมื่อมี, และ `source` (`registration`, `front-update`, `line-liff-bind`)

บันทึกต้องเกิดจาก checkbox/ปุ่มยืนยันที่ผู้ใช้กดเอง, ตรวจ version ฝั่ง server, และคงเป็นประวัติ append-only; ไม่บันทึกการเปิดดูหรือการปฏิเสธเป็นการยอมรับ ไม่มีการ backfill PDPA record เก่าให้เป็น Terms acceptance และไม่บันทึก IP ที่เชื่อจาก client header โดยไม่ผ่าน trusted proxy configuration

Schema ที่ต้อง apply ก่อน deploy API อยู่ใน [API/Database/terms-acceptances.sql](../API/Database/terms-acceptances.sql) พร้อม entity และ API endpoint ปัจจุบัน ข้อมูล acceptance มีข้อมูลส่วนบุคคล ควรกำหนดสิทธิ์อ่าน ระยะเวลาเก็บ และการส่งออกตามนโยบาย retention ขององค์กร

## Acceptance checklist ก่อน production

- [ ] ฝ่ายกฎหมายอนุมัติทั้งภาษาไทยและอังกฤษ; ระบุคู่สัญญา/ช่องทางติดต่อ/กฎหมาย/ข้อกำหนดการชำระเงินและคืนเงินที่ถูกต้อง
- [ ] เผยแพร่ Privacy Notice จริงและตรวจว่า checkbox PDPA สะท้อนฐานกฎหมาย/วัตถุประสงค์จริง (ไม่ใช่เพียงยืนยันว่าอ่านแล้ว)
- [ ] ใช้ version, effective date และ content hash ชุดเดียวกันทุกแอป; migration SQL ถูก apply ก่อน API deploy
- [ ] ทดสอบสมัครใหม่, user เก่าที่ login, version เปลี่ยน, stale-version submit, ปฏิเสธ, network fail และ LINE link code
- [ ] ตรวจว่าไม่มี protected API endpoint ที่ข้ามการตรวจ current acceptance และประวัติเดิมไม่ถูกแก้ไข
